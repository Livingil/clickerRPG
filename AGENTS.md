# Правила работы с проектом ClickerRPG

Эти правила обязательны для Codex/AI-ассистента при работе в этом репозитории.

## Роль ассистента

- Работать как инженер проекта: читать текущую архитектуру перед правками, не делать изменения вслепую.
- Сначала понимать существующие системы Godot/GDScript, затем менять минимально необходимую часть.
- Не переписывать большие блоки ради вкуса. Рефакторить только когда это снижает реальную сложность или убирает дубли логики.
- Не откатывать чужие или пользовательские изменения без прямой команды.

## Важное правило по тестам

- Не запускать баланс-тесты, smoke-runner-ы, gameplay-runner-ы, долгие headless-сцены и симуляции без прямой просьбы пользователя.
- Если пользователь просит только анализ, сводку или мнение, не запускать тесты.
- После правок можно предложить проверку, но не запускать ее самостоятельно без подтверждения.
- Если пользователь явно просит проверить/прогнать тест, запускать только нужный runner и после завершения проверять, что headless Godot не остался висеть.

## Godot и процессы

- Godot executable в этом проекте обычно: `C:\Users\Владимир\Desktop\Godot_v4.6.2-stable_win64.exe`.
- Не оставлять фоновые headless-процессы Godot.
- После запуска headless Godot проверять только процессы с:
  - `Name == Godot_v4.6.2-stable_win64.exe`
  - `CommandLine` содержит `--headless`
- Останавливать только такие headless-процессы, не трогать обычный редактор Godot пользователя.

## Кодировка и русский текст

- Все текстовые файлы сохранять в UTF-8.
- Русские строки должны оставаться читаемой кириллицей.
- Не добавлять битый текст вида `РџСЂ...`, `РЎ...`, `Р ...`.
- Если найден поврежденный русский текст в затронутом файле, сначала исправить кодировку/текст, затем продолжать функциональные правки.
- Для новых файлов использовать читаемый русский или английский, без смешивания кодировок.

## Архитектура проекта

- `autoload/game_state.gd` - фасад глобального состояния игрока: хранит account/run state, делегирует прогресс, экономику, школы, снаряжение, артефакты, Echo, рекламу, престиж и сохранение профильным сервисам.
- `autoload/game_constants.gd` - главный источник чисел баланса и общих констант.
- `scripts/gameplay/wave_controller.gd` - волны, спавн, боссы, milestone-логика.
- `scripts/enemies/enemy.gd` - поведение врагов, типы мобов, атаки, эффекты школ на мобах.
- `scripts/hero/` - герой, атака, движение и применение боевых статов.
- `scripts/abilities/` - активные навыки школ.
- `scripts/ui/` - интерфейс. UI должен читать готовые данные из `GameState`, а не дублировать формулы баланса.
- `scripts/dev/` и `scenes/dev/` - dev-runner-ы и симуляции. Не запускать без прямой просьбы.

## Компоненты и ответственность

- Один файл - одна понятная ответственность.
- Целевой размер обычного файла: 300-500 строк. Если файл выходит за 500 строк, сначала проверить смешение ответственностей и вынести самостоятельные части в отдельные сервисы, rules, builders или UI-компоненты.
- Файл меньше 300 строк не является обязательной целью: маленький файл допустим, если ответственность завершенная и понятная.
- Не дробить файл механически только ради количества строк. Разделение должно улучшать ответственность, повторное использование, тестируемость или читаемость.
- Если файл начинает управлять несколькими независимыми задачами, выделить отдельный компонент, helper или data-driven таблицу.
- Переиспользуемую логику выносить в отдельные функции/классы/компоненты, а не копировать между UI, gameplay и dev-симуляторами.
- UI-компоненты должны отвечать за отображение и пользовательские действия, а не за расчет баланса, прогресса или боевых формул.
- Gameplay-компоненты должны отвечать за поведение в бою, а не за сохранения, UI-тексты или экономику.
- Балансные формулы и константы должны жить в одном источнике правды: `GameConstants`, `GameState`, `SchoolRules` или явной data-driven таблице.
- Сцены Godot должны быть композиционными: сложное поведение лучше выносить в скрипты-компоненты, которые можно переиспользовать и отдельно проверять.
- Не создавать универсальный "god object". Если компонент становится слишком большим, сначала определить его реальные ответственности и разделить по ним.

## Баланс

- Числа баланса держать в `GameConstants` или data-driven таблицах `GameState`/`SchoolRules`.
- Не дублировать одну и ту же формулу в runtime и симуляторе. Если дубли уже есть, при правке синхронизировать оба места или явно отметить риск.
- Для бесконечного роста избегать линейных бесконечных бонусов без soft-cap, hard-cap или затухающей формулы.
- Награды, силу врагов, Echo, экипировку, школы и престиж рассматривать как связанную систему.
- Не усиливать врага и одновременно его награду, если цель - создать стену прогресса.

## UI

- Интерфейс должен отвечать на вопрос игрока: что у меня есть, что даст следующий апгрейд, где ближайшая веха.
- Не перегружать свернутые строки длинными описаниями.
- Подробности показывать по раскрытию/отдельному блоку.
- Русские UI-строки держать короткими и читаемыми.

## Сохранения

- При изменении прогресса игрока проверять `build_save_data()` и `apply_save_data()`.
- Новые постоянные поля должны сохраняться и восстанавливаться.
- При изменении формата сохранения учитывать `SAVE_VERSION` и миграции.
- На Windows закрывать `FileAccess` перед удалением/переименованием файла сохранения.

## Перед завершением задачи

- Сообщить, какие файлы изменены по смыслу.
- Сообщить, какие проверки не запускались из-за правила "не запускать тесты без просьбы".
- Если проверка нужна, предложить конкретную команду/runner, но не запускать без разрешения.
